## 1. Platform and configuration

| Concern | Choice |
|---|---|
| Framework | Next.js 16.4 (App Router, TypeScript, `src/` layout) |
| Database | PostgreSQL 18 on Neon (region ap-southeast-1) |
| ORM | Prisma 7.10.1 (stable). The npm `latest` tag currently points to an 8.0 release candidate, which was deliberately **not** used. |
| Client generation | `prisma-client` generator → `src/generated/prisma` (git-ignored, regenerated on `npm install` via `postinstall`) |
| Runtime connection | `@prisma/adapter-neon` with the **pooled** `DATABASE_URL` (`src/lib/db.ts`) |
| CLI / migrations | `prisma.config.ts` → **direct** (non-pooled) `DIRECT_URL`. Env files are loaded with `@next/env`, the same loader Next.js uses. |
| TLS | `sslmode=require` on both URLs (plus `channel_binding=require` on the pooled URL) |
| Authentication | Better Auth 1.7 (email + password, scrypt hashing) with the Prisma adapter |
| Validation | Zod 4 (`src/lib/validation/`) |
| File storage | Private AWS S3 bucket, project prefix `ss-dimri/` (`src/lib/storage/s3.ts`) |

## 2. Conventions

- **Names**: Prisma models are PascalCase and fields camelCase; database tables and columns are snake_case via `@@map` / `@map`.
- **Primary keys**: `uuid` columns. Values are UUIDv7 (time-ordered, index-friendly) generated by Prisma Client; seed SQL uses `gen_random_uuid()`.
- **Human-readable IDs**: where the notes say “ID” for a business record, a separate optional code column is provided (`clients.client_code`, `services.service_code`, `employees.temporary_employee_code` / `permanent_employee_code`), unique per organization. The UUID remains the internal key.
- **Timestamps**: `timestamptz(3)`, stored in **UTC**. Every mutable table has `created_at` and `updated_at` (`updated_at` is maintained by Prisma Client).
- **Calendar dates**: business dates (attendance date, work date, due dates, periods) are `date` columns, interpreted in the organization’s timezone `organizations.timezone` (default `Asia/Kolkata`). Convert “today” in that timezone before writing.
- **Money**: `numeric(14,2)`; never floating point. Percentages `numeric(5,2)`; leave counts `numeric(5,1)` (half days).
- **Coordinates**: `numeric(9,6)` (≈ 0.1 m precision), range-checked.
- **Enums vs lookup tables**: PostgreSQL enums are used for stable, confirmed or purely technical categories (task priority, attendance status, pending status…). **Configurable lookup tables** are used where the client has not finalised the options: `nature_of_user_options`, `designations`, `employee_nature_options`, `departments`. Enums marked *PROVISIONAL* in the schema comments are reversible modelling choices (see open questions).
- **Referential actions** (deliberate, per relation — the generated reference lists each one):
  - `CASCADE` for records owned by a parent (GSTINs, addresses, bank accounts, documents, task attachments/reminders/activities).
  - `RESTRICT` for operational history (attendance, timesheets, tasks, allocations, reports, dues) so history cannot be silently destroyed.
  - `SET NULL` for optional references (approver, uploader, optional links).
- **Check constraints** (hand-written in the initial migration; Prisma does not model them, so they cause no drift): date ordering (end ≥ start), non-negative amounts/counts, coordinate ranges, allocation % 0–100, no self-reporting, permanent employee code present when `id_type = PERMANENT`, licensed user limit ≥ 1. No unconfirmed business rule is enforced by a constraint.

## 3. Multi-tenancy and access control

- `organizations` is the tenant. Every top-level business table carries `organization_id` (indexed). Child tables (e.g. `client_gst_registrations`, `employee_addresses`) are scoped through their parent.
- Users authenticate once (`users`) and are granted access per organization through `organization_memberships` (role + status). A membership can link to the staff record (`employee_id`, unique).
- **All data access must filter by the caller’s organization** — derived from the session’s membership, never from client input. This will be centralised in a scoped data-access layer when the API is built (after the DFD). Hiding fields in the UI is not treated as security.
- `organizations.access_mode` (SINGLE_USER / MULTI_USER) and `licensed_user_limit` (sub-users / licenses) are checked by application logic when memberships are created.

## 4. Sensitive data

| Data | Handling |
|---|---|
| Passwords | Never in business tables. Better Auth stores a scrypt hash in `accounts.password` (verified: 161-char hash, not plaintext). |
| Aadhaar numbers | AES-256-GCM encrypted (`*_aadhaar_encrypted`) with `aadhaar_last4` for display. Key: `DATA_ENCRYPTION_KEY` (`src/lib/security/encryption.ts`). Authenticated encryption — tampering is detected. |
| Bank account numbers | Encrypted the same way (`account_number_encrypted` + `account_number_last4`). |
| PAN | Stored in clear (needed for lookup/indexing), but treated as sensitive: never logged, never returned by broad list APIs. |
| Identity / employment documents | Private S3 objects; access only through 5-minute pre-signed URLs issued after an authorization check. |
| Audit | `audit_logs` records approvals and sensitive changes (actor, action, entity). Its `metadata` must never contain secrets or raw identifiers. |
| Credentials | Only in `.env.local` (git-ignored). `.env.example` has placeholders. Scripts redact hosts and never print connection strings. |

> **Key management:** losing `DATA_ENCRYPTION_KEY` makes encrypted fields unrecoverable. Store it in the deployment platform’s secret manager and back it up securely. The ciphertext format is versioned (`v1.`) to allow key rotation later.

## 5. File storage

- Binary content is **never** stored in PostgreSQL. `stored_files` holds metadata: bucket, `object_key` (unique), original name, MIME type, size, optional SHA-256, uploader, organization.
- Object keys: `ss-dimri/org/<organizationId>/<area>/<ownerId>/<uuid>.<ext>` — the original file name lives only in the database.
- Uploads/downloads use short-lived pre-signed URLs with server-side encryption (SSE-S3 AES256). The bucket is shared with another project; this application only reads/writes under `ss-dimri/`.
- **Single-slot uploads** (profile picture, MSME/ESI/PF certificate, Aadhaar/PAN document, bank book, attendance photos) are direct unique FK columns. **Open-ended uploads** (client certificates, employee letters, organization leave policy, task attachments) use document tables with a `type` column. Each `stored_files` row is used by at most one owner slot (unique FKs).

## 7. Derived (calculated) values — not stored

Helpers in `src/lib/domain/derived.ts`.

| Requirement | Derivation |
|---|---|
| Attendance work hours | `time_out − time_in` |
| Task overdue | `due_at < now()` and status not COMPLETED/CANCELLED |
| Days pending | `(closed_at or today) − requested_on` |
| Employee age | from `date_of_birth` |
| Client fees total | Σ `client_services.agreed_fee` for the client (open question: or a contract total?) |
| Actual employee / client counts | `count(*)` of `employees` / `clients` (declared counts are stored separately) |
| Leave used / remaining | approved `leave_requests` and attendance `LEAVE` days vs `leave_balances.allowed_paid_leaves` |
| Availability / calendar colours | from `team_allocations` (dates, %), `attendance_records`, `leave_requests` |

## 8. Workflows supported by the schema

- **Client quick registration**: insert `clients` with `status = PENDING_APPROVAL` and only the required fields; remaining fields are nullable and can be filled later (`details_completed_at`). Admin approval sets `status = ACTIVE`, `approved_at`, `approved_by_id` on the **same row** (no duplicate record) and writes an `audit_logs` entry. Rejection sets `REJECTED`, `rejected_at/by`, `rejection_reason`.
- **Employee temporary → permanent**: created with `id_type = TEMPORARY`, `temporary_employee_code`, `approval_status = PENDING`, `employment_status = PROBATION`, probation dates from `organizations.default_probation_days` (default 7). Approval assigns `permanent_employee_code`, `id_type = PERMANENT`, `permanent_id_assigned_at`, `approved_at/by`. The temporary code is retained for traceability.
- **Employee not approved**: either `approval_status = UNDER_REVIEW` (with `review_notes`) or `REJECTED`. A rejected temporary record *can* be hard-deleted: owned profile rows cascade, but operational history (attendance, timesheets, tasks…) uses RESTRICT, so a person with real work history cannot be erased accidentally. Final policy is an open question.
- **Allocation change**: end the current `team_allocations` row (`status = ENDED`, `end_date`) and create a new one with `replaces_allocation_id` and `change_reason`.
- **Retainer renewal**: a new `client_services` row with `renewed_from_id` pointing at the previous engagement. Expiry rules are not enforced until confirmed.

## 9. Migration workflow

- Migration history in `prisma/migrations/` is the source of truth. The initial migration `20261026065237_init` contains the generated DDL plus reviewed hand-written additions (constitution seed rows, CHECK constraints).
- Development: edit `schema.prisma` → `npm run db:migrate:dev -- --name <change>` (uses a temporary shadow database) → review SQL → commit.
- Deployment: `npm run db:migrate:deploy` (applies pending migrations only; never resets).
- Drift check: `npm run db:drift` (exit code ≠ 0 if the live DB differs from the schema).
- Never use `prisma migrate reset` or `db push` against the shared Neon database.

## 13. Migration 5 — `20261026210000_attendance_one_per_day` (additive)

Replaces the plain index `attendance_records(employee_id, attendance_date)` with a **unique** index on the same columns: one attendance record per employee per day, so a double submit or a second browser tab cannot record two mark-ins. Pre-check `scripts/check-attendance-duplicates.ts` (read-only) reported 0 duplicate groups before it was applied. No data was changed. The application also uses conditional writes, so a duplicate attempt gets a clear message instead of an error.

## 14. Migration 6 — `20261026230000_approval_grace_period` (additive)

`organizations.approval_grace_days INTEGER NOT NULL DEFAULT 7` with a CHECK of 0–90 days: how long a pending staff member or business may use the account before approval (owner decision, 26 Oct 2026). No existing data changed.
